Protocol guide

MCP & JSON-RPC, explained

How the Model Context Protocol lets AI assistants use tools and data — and how every message is a tiny JSON-RPC 2.0 object. Written for newcomers and integrators alike.

💡 In one line: MCP (Model Context Protocol) is an open standard — think “USB-C for AI” — that lets an AI assistant securely discover and use external tools and data through one common interface. Under the hood it's just JSON-RPC, and with this gateway you can build your own tool in minutes.

The three roles

  • Host — the AI app a person uses (an IDE, chat app, or agent). It runs one or more clients.
  • Client — lives inside the host and holds a 1:1 connection to a single server.
  • Server — exposes capabilities: tools (actions), resources (data), and prompts (templates).

How the pieces talk

Every message is a JSON-RPC 2.0 object carried over a transport:

  • stdio — the host launches the server as a subprocess and exchanges messages over stdin/stdout. Great for local tools.
  • Streamable HTTP — the server is a web endpoint and can stream responses over Server-Sent Events. Great for remote, shared servers.

Where this gateway fits

This is a multi-tenant MCP front door. The fastest path from zero to a working tool is to write one; connecting servers you already run is the advanced step. It adds:

  • Code tools (start here) — author a Python function that runs sandboxed in WebAssembly and is instantly exposed as a normal MCP tool. No infra, no deploy.
  • One endpoint aggregating many MCP servers, with per-tenant isolation and RBAC.
  • Semantic discovery — tools/search ranks the right tool out of a large catalog.
  • Guardrails & approvals for sensitive actions, plus full telemetry.
💡 In one line: JSON-RPC 2.0 is a tiny convention for “call a method, get a result.” Each message is one JSON object that is a request, a response, or a notification.

The four message shapes

Request (expects a reply) 
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
Response · success 
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "tools": [] }
}
Response · error 
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32601, "message": "Method not found" }
}
Notification · no id, no reply 
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}

Field reference

FieldTypeMeaning
jsonrpcstringAlways "2.0".
idstring / numberCorrelates a response to its request. Omit it to send a notification.
methodstringThe operation to invoke, e.g. tools/call.
paramsobjectArguments for the method (an object in MCP).
resultanyPresent on success — mutually exclusive with error.
errorobjectPresent on failure: { code, message, data? }.

Error codes

CodeMeaning
-32700Parse error — invalid JSON.
-32600Invalid Request.
-32601Method not found.
-32602Invalid params.
-32603Internal error.
-32000…-32099Server-defined. This gateway uses -32001 unauthorized, -32003 forbidden, -32029 rate-limited, -32004 upstream timeout.
💡 In one line: A session always begins with an initialize handshake; then the client discovers and uses the server’s primitives.

Session lifecycle

1
Client → initialize

Sends its protocolVersion, its capabilities, and clientInfo.

2
Server → result

Replies with its protocolVersion, capabilities, and serverInfo.

3
Client → notifications/initialized

Confirms the handshake; normal operation may begin.

4
Operate

List/call tools, read resources, get prompts. Either side may send notifications.

Common protocol methods

MethodPurpose
initializeNegotiate version & capabilities (the first call).
tools/listDiscover available tools and their JSON-Schema inputs.
tools/callExecute a tool by name with arguments.
resources/list · resources/readBrowse and fetch data resources.
prompts/list · prompts/getBrowse and render prompt templates.
pingLiveness check.
notifications/tools/list_changedServer → client: “the catalog changed, re-list.”

Runtime guide

The magic of context

Every code tool runs in a network-isolated wasm sandbox — yet gets a tenant-scoped database and encrypted secrets through one tiny object. No credentials, no connection strings, no sockets.

💡 In one line: context hands your function four superpowers — context.db, context.env, context.tools, and opt-in context.http — with zero credentials and no raw sockets.
🗄️
context.db

Tenant-scoped MongoDB. Every read/write is relayed through the host, isolated to your tenant, and gated by the tool's action_type.

🔐
context.env

Per-server encrypted secrets. Set them in Edit → Secrets; read them with context.env.get(...). Never logged, never in process env.

🧩
context.tools

Call sibling tools in your tenant namespace: context.tools.<server>.<tool>(...). Re-authorized against you, code-only, depth-bounded.

🌐
context.http

Opt-in outbound HTTPS, relayed through the host: deny-by-default allowlist, SSRF-screened + IP-pinned, with host-side secret injection via auth="ENV_KEY".

Why it's safe

  • No secrets in code — the sandbox never sees a connection string or API key.
  • No network — the wasm jail has no sockets; the host performs every DB op on your behalf.
  • Scoped & gated — a read tool literally cannot call insert_one; the host rejects it.
  • BSON-aware — return MongoDB documents, ObjectIds, and datetimes directly and they serialize to JSON for you.

Take it with you

Use Export server (.zip) (in the server editor) to download a runnable FastMCP project with every tool wired up — context is reconstructed locally, and context.tools calls between your tools keep working. Secrets are never exported.

The whole surface, at a glance 
context.db["collection"]              # or context.db.collection
context.db.ObjectId("656f...")        # build a BSON id for a query
context.env.get("API_KEY", "")        # per-server encrypted secret
context.tools.billing.charge(amount=5)  # call a sibling tool
💡 Use it like a PyMongo collection. Reads return plain dicts/lists; find() is capped by SANDBOX_DB_MAX_DOCS.

Read

find_one + ObjectId 
def by_id(user_id: str) -> dict:
    # context.db.ObjectId builds the BSON id — it lives on the db
    return context.db.users.find_one({"_id": context.db.ObjectId(user_id)}) or {}
aggregate (top targets) 
def top_targets(limit: int = 5) -> dict:
    rows = context.db.clicks.aggregate([
        {"$group": {"_id": "$target", "count": {"$sum": 1}}},
        {"$sort": {"count": -1}},
        {"$limit": max(1, min(int(limit), 25))},
    ])
    return {"top": [{"target": r["_id"], "count": r["count"]} for r in rows]}

Available operations

  • read: find_one, find, aggregate, count_documents, distinct
  • write: the above plus insert_one, insert_many, update_one, update_many
  • destructive: the above plus delete_one, delete_many

Your tool's action type decides which of these the host will run — anything outside the tier is rejected before it touches the database.

💡 Each MCP server has its own encrypted .env. Values are written once in the UI and only ever decrypted into the sandbox at runtime.

Read a secret

context.env 
def current_label() -> dict:
    # falls back to a default when the key isn't configured
    return {"label": context.env.get("CLICK_LABEL", "anonymous")}

Set a value

  1. Open the server with Edit, then the Secrets tab.
  2. Add a KEY / value pair and save.
  3. Read it anywhere in that server's tools via context.env["KEY"].

Values are encrypted at rest, scoped to the server, and never returned by the admin API after they're written.

💡 Your tenant is a namespace of servers, each with tools. context.tools lets one tool call another — compose small tools into a workflow instead of duplicating logic.

Call a sibling tool

namespace → server → tool 
def track_and_report(target: str, source: str = "web") -> dict:
    # Each call is relayed to the host, re-authorized, and run in its own sandbox.
    recorded = context.tools.analytics.track_click(target=target, source=source)
    stats = context.tools.analytics.get_click_stats(limit=5)
    return {"recorded": recorded, "leaderboard": stats.get("top_targets", [])}

Three equivalent forms

pick whichever reads best 
context.tools.analytics.track_click(target="home")     # attribute style
context.tools["my-funcs"]["track-click"](target="home")  # bracket style (hyphens)
context.call("analytics", "track_click", target="home")  # explicit

Pass arguments by keyword — they map to the target function's parameters. The return value is exactly what the other tool returns (BSON-aware, JSON-safe).

How it stays safe

  • Re-authorized as you — the call uses your scopes, so you can only reach tools you could already call directly.
  • Code tools only — siblings must be transport="code" in the same tenant; network/proxied tools stay unreachable.
  • No confirmation-gated tools — anything that needs a human approval can't be triggered programmatically.
  • Bounded — depth + per-run call budgets stop runaway or cyclic fan-out; a tool that calls itself fails closed.

A blocked call raises a clear error you can try/except (forbidden, confirmation_required, tool_not_callable, tool_call_depth_exceeded, …). Enable with SANDBOX_TOOL_BRIDGE_ENABLED.

💡 Opt-in outbound HTTPS for code tools — the wasm jail still has no sockets. Each call is relayed to the host and made through the same egress firewall the gateway uses: deny-by-default allowlist, SSRF denylist, DNS-rebinding-proof IP pinning (re-checked on every redirect).

Make a request

GET + JSON 
def fx_rate(base: str = "USD") -> dict:
    # Host screens the URL against the egress allowlist, pins a validated IP,
    # then makes the call. Response body is capped by SANDBOX_HTTP_MAX_RESPONSE_BYTES.
    resp = context.http.get("https://api.example.com/rates", params={"base": base})
    if not resp.ok:
        raise ValueError(f"upstream {resp.status}")
    return resp.json()

Authenticated calls — the secret never enters your code

auth="ENV_KEY" 
def me() -> dict:
    # You pass the NAME of a secret (set in Edit → Secrets). The host looks it up
    # and attaches "Authorization: Bearer <value>" — the value is never in your
    # source, the URL, logs, or the response you get back.
    return context.http.get("https://api.example.com/me", auth="EXAMPLE_TOKEN").json()
    # custom header: auth={"key": "EXAMPLE_TOKEN", "header": "X-Api-Key", "scheme": ""}

Methods & your action type

  • read tools: get, head only.
  • write / destructive tools: also post, put, patch, delete (send a body with json= or data=).

The response exposes .status, .ok, .headers, .text, .content, and .json() (cookies and hop-by-hop headers are stripped).

How it stays safe

  • https only — plaintext http:// and non-HTTP schemes are rejected.
  • Deny-by-default — a host is reachable only if a tenant admin adds it to the egress allowlist and it sits under the platform ceiling (EGRESS_GLOBAL_ALLOWLIST). An empty allowlist blocks everything.
  • SSRF-screened — internal / private / link-local addresses are always denied, even via a redirect or a rebind.
  • Bounded — per-invocation call budget, per-call timeout, request/response size caps, a per-host circuit breaker, and per-tenant concurrency limits.

A blocked call raises a clear error you can try/except (egress_blocked, http_scheme_forbidden, http_method_forbidden, http_auth_unknown_key, http_response_too_large, http_call_limit, http_timeout, …). Enable with SANDBOX_HTTP_BRIDGE_ENABLED.

💡 The clever part: writes return PyMongo-style result objects, and you can return raw BSON types straight out of your function.

Write results

insert → .inserted_id 
def track_click(target: str) -> dict:
    result = context.db.clicks.insert_one({"target": target})
    # ObjectId is auto-serialized to a string in the response
    return {"click_id": result.inserted_id}

Every write returns a result object with attribute and dict access:

  • insert_one → .inserted_id
  • insert_many → .inserted_ids
  • update_one / update_many → .matched_count, .modified_count, .upserted_id
  • delete_one / delete_many → .deleted_count
  • all of them → .acknowledged

Return Mongo types directly

BSON-aware serialization 
from datetime import datetime, timezone

def latest(user_id: str) -> dict:
    doc = context.db.users.find_one({"_id": context.db.ObjectId(user_id)})
    # _id (ObjectId) and any datetime fields serialize cleanly — no manual str() needed
    return {"user": doc, "checked_at": datetime.now(timezone.utc)}

ObjectId becomes a string and datetime becomes an ISO-8601 UTC timestamp automatically, so you can hand documents straight back to the caller.

Tenant curation

Tool policy —

Curate exactly which tools a tenant can discover and call. An empty allowlist means unrestricted; a disabled tool is always hidden and refused, even to admins.

Tenant curation

Code packages —

Choose which PyPI distributions this tenant's code tools may install in the sandbox. What actually installs is this list intersected with the platform ceiling (SANDBOX_ALLOWED_REQUIREMENTS). An empty list means standard library only.
